# DeepSeek Harness Lanyard

[English](README.md) | 简体中文

用手机打开 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 的 Web 界面。

`dsh` 照常在电脑上跑，手机扫一下二维码，界面就在那儿了：走自己家的网络，全程 TLS 加密。网络里的其他设备过不了 dsh 的登录这一关；电脑本机的浏览器标签页，地址也和原来一模一样。

这个插件只干这一件事。它不是网关，不是反向代理，也不能让你从外网连回自己的机器。

## 为什么非得装个插件

`dsh web` 默认只绑定 `127.0.0.1`，并且直接拒绝 `--host 0.0.0.0`。原因很实际：`/api` 会以 `dsh` 进程的身份执行命令。从 0.1.2 起，dsh 自己就会给每个浏览器做认证——启动行里那个带 `?token=` 的链接就是用来登录的——但它依然不肯对局域网提供服务：走的是明文 HTTP，而且只要浏览器登录过，就把它当成坐在键盘前的那个人。

这个插件解除这道限制，并补上局域网监听仍然缺的东西：TLS；在网络设备能碰到的每一条路由前面，都先过一遍 dsh 自己的会话校验；配置类接口仍然只留在本机。它自己不另设任何登录。**不改动 Harness 源码**，以普通插件包的形式安装。

## 安装

```sh
dsh plugin --profile web add @koalafacts/deepseek-harness-lanyard
```

安装前请先运行 `npm view @koalafacts/deepseek-harness-lanyard version` 核对 npm 仓库里的实际版本。npm 上的 `0.0.0` 只是占位包，**并不能正常使用**；源码仓库中写着较高版本，不等于那个版本已经发布。只有 npm 仓库出现真正的发布版本，才能使用上面的安装命令。

### npm 仍只有占位包时，安装本地打包版本

如果 `npm view @koalafacts/deepseek-harness-lanyard version` 仍然只显示 `0.0.0`，可以使用**从本仓库源码生成的本地安装包**，不要安装那个不能工作的占位版本。以下命令在**运行 dsh 的电脑**上执行，而不是在手机上执行。需要事先安装好 `dsh` CLI、Node.js 22.19+（22.x 系列）或 24+，以及 pnpm 10。

```sh
git clone https://github.com/KoalaFacts/deepseek-harness-lanyard.git
cd deepseek-harness-lanyard
pnpm install --frozen-lockfile
npm run check
pnpm pack --pack-destination .
dsh plugin --profile web add "$PWD/koalafacts-deepseek-harness-lanyard-0.2.0.tgz"
```

上面的 `.tgz` 文件名对应当前 `package.json` 的 `0.2.0` 版本；以后版本号变了，就以 `pnpm pack` 生成的实际文件名为准。建议同时记录 `git rev-parse HEAD`，方便日后确认自己安装的是哪一个源码提交。

如果使用 **Windows PowerShell**，先照常运行前面的 `git clone`、冻结依赖安装、`npm run check` 和 `pnpm pack`，然后**只替换最后一条** `dsh plugin ... add` 命令。下面会从 `package.json` 读取实际版本，避免猜测文件名或误装目录里更旧的安装包：

```powershell
$version = (Get-Content -LiteralPath .\package.json -Raw | ConvertFrom-Json).version
$tarball = Join-Path (Get-Location) "koalafacts-deepseek-harness-lanyard-$version.tgz"
if (-not (Test-Path -LiteralPath $tarball -PathType Leaf)) {
  throw "Missing local tarball: $tarball. Run pnpm pack first."
}
dsh plugin --profile web add $tarball
```

这仍然只在运行 DSH 的电脑上安装本地打包产物，不代表 npm 已正式发布，也不会自动开放局域网监听。

这种方式**不会向 npm 发布任何东西，也不会自动开放局域网**。项目现有的真实 DSH 端到端测试采用同类本地 tarball 在干净环境安装，但这不代表正式 npm 发布或实体手机测试已经完成。安装之后仍要按照下文指定可信局域网地址启动 dsh，并遵循 TLS 证书指纹核对和配对步骤。

### 下载未发布的 CI 安装候选包

如果暂时无法在本机从源码构建，可以打开 [CI 工作流](https://github.com/KoalaFacts/deepseek-harness-lanyard/actions/workflows/ci.yml)，选择一次 **`main` 分支全部成功的运行**。先确认 **check、e2e、browser、candidate-consumer** 四项全部通过，再到 *Artifacts* 下载 **`unpublished-lanyard-<完整提交 SHA>`**。在运行 dsh 的电脑上解压 ZIP，里面有可安装的 `.tgz`、`SHA256SUMS` 和 `SOURCE_SHA`。确认 `SOURCE_SHA` 与该次成功运行的完整提交 SHA 一致；也可运行 `sha256sum -c SHA256SUMS`（macOS：`shasum -a 256 -c SHA256SUMS`）检查文件有无意外损坏。然后用 `dsh plugin --profile web add "/实际解压目录/安装包.tgz"` 安装，替换成文件的真实绝对路径。

这种产物**只会在 main 推送时生成**，保存七天，**不是 npm 正式发布、独立签名的来源证明，也不是实体手机验收结果**。与安装包放在同一 ZIP 的校验和仅用于发现意外损坏，不能单独证明来源可信；必须在 GitHub 上核对工作流和提交。安装后仍需显式提供 `--host <本机实际局域网 IPv4>` 才会开放局域网服务。

如果 Web 侧边栏里有 **Plugins（插件）** 页面，也可以直接在那里按同样的包名安装，它会显示为 *Lanyard 手机访问*。

光装上什么都不会变：dsh 照旧只服务本机。要不要对局域网提供服务，每次启动时由你自己决定：

```sh
dsh --profile web --host 192.168.1.5
```

如果启动提示指定的 IPv4 地址**并未分配给这台电脑**，请检查当前 Wi-Fi 或以太网的 IPv4 地址（例如重新连接网络或 DHCP 更新后），再使用正确的 `--host` 重试。Lanyard 不会悄悄改为监听另一块网卡。

请把示例中的 `192.168.1.5` 换成这台电脑实际拥有的 IPv4 地址（一般是 Wi-Fi 或以太网地址），不要直接照抄示例 IP。dsh 0.2.1 预发布载体会拒绝通配地址 `0.0.0.0`；较早的 0.2.0 版本还支持 `dsh --profile web --host 0.0.0.0`，但这会监听所有网卡。Lanyard 保留上游的限制：指定具体 IP 时，TLS 监听只使用该网卡。目前尚不支持 IPv6 监听。不传参数时仍然只服务本机。指定具体 IPv4 地址时，自动生成的 TLS 证书只包含该绑定地址；无关的 VPN 或容器网卡变化不会在下次重启时迫使手机重新接受证书。若改用另一个局域网绑定地址，仍须生成新证书并重新核对指纹；旧版通配地址监听继续覆盖全部网卡。 仅局域网地址变化时，重新签发证书会保留原有匹配的私钥；即使证书写入中断，旧证书与私钥仍保持配对。新证书的指纹仍会变化，必须重新核对。若替换证书时在写入临时文件后失败，Lanyard 会清理本次创建的临时文件，允许在同一进程内重试；预先存在的临时文件仍会被保留，并阻止自动覆盖。首次签发证书时，如果证书写入失败，Lanyard 也只会在证书尚未出现、私钥仍与本次生成内容相同的条件下清理本次新建的私钥，以便故障解决后重试；若清理自身失败，不完整证书对仍会触发拒绝启动。

Lanyard 用同目录的排他锁目录（`cert.pem.lanyard-lock` 和 `key.pem.lanyard-lock`）协调本库的证书写入者。并发启动会明确报告 TLS 材料正忙；活动写入者结束后可重试。进程崩溃或锁清理失败可能留下锁：Lanyard 不会自动删除或抢占。操作者须先确认没有 Lanyard 写入者活动，再移除遗留锁。这项协调不保证阻止其他未遵守锁协议的程序替换文件。 即使复用已有证书对，也需要对父目录有写权限以获取锁。直接调用 API 时须使用一致的最终文件名；目录别名会规范化，但不支持 Windows 文件名末尾点号或空格产生的别名。

`--tls-cert <file> --tls-key <file>` 可以为 TLS 前端提供已有的 PEM 证书和私钥文件，替代自动生成；两者必须同时提供。每条路径解析后必须指向普通文件：指向普通 PEM 文件的证书管理器符号链接可以使用，但目录、设备文件或命名管道会在读取前被拒绝（读取无写入方的管道可能使启动卡住）。Lanyard 不会自动更新或覆盖这些操作者管理的文件。本机监听仍然使用明文 HTTP。在支持此功能的 dsh 版本中，`--public-url <url>` 只修改公布的根 URL，不授予 Host 信任；需要时另行使用 `--trusted-host`。它不会修改 Lanyard 直接连接的 TLS 配对地址。

直接组合载体时，`tls: null` 与省略 `tls` 一样，表示没有显式提供 PEM 证书和私钥。对网络开放监听仍然必须提供自动生成或显式指定的 TLS 文件。

本机照样用原来的 `http://127.0.0.1:3080`；网络上的设备走 TLS，用单独的端口，默认 3443。启动时会打印配对链接、证书指纹，以及链接对应的二维码。如果启动就绪被延迟，Lanyard 会重新读取当前监听地址和局域网地址列表，避免给手机打印旧 IP 的配对链接。如果 DSH 在启动就绪前替换了浏览器认证服务，Lanyard 会使用当前服务生成配对令牌，不打印已失效的旧链接；如果认证服务已不存在，则不输出链接或二维码，并提示重启 DSH。如果启动就绪时读取 TLS 服务发生异常，Lanyard 会输出不含敏感信息的固定恢复提示，不会泄露上游异常内容或留下未处理的就绪 Promise 错误：

```
lanyard: serving your network over TLS on port 3443 — do not open the (LAN: …) link on the dsh web line: it is plain http and carries the launch token
lanyard: pair a device by opening https://192.168.1.5:3443/?token=<launch token> once
lanyard: the phone should show certificate SHA-256 7F:52:AF:73:DB:4B:08:A0:9E:56:2D:83:B1:C5:7D:AF:0C:ED:3D:9A:F8:88:B9:B8:8C:27:3A:7A:2A:02:E4:B3 — if it ever shows another, do not continue
lanyard: or scan this with the phone
```

dsh 自己那行 `dsh web:` 里的 `(LAN: …)` 链接别去点：它走明文 http，还带着启动令牌。正常情况下没有任何东西会应答它，但如果有人在网络里冒充你的电脑，就能拿到令牌。 即使使用明确的 `--host <局域网 IPv4>`（而不是旧版通配地址），这条警告也适用；手机只能打开 Lanyard 提供且已核对证书指纹的 HTTPS 配对链接。

### 命令行参数

| 参数 | |
|---|---|
| `--host <局域网 IPv4>` | 在指定的可信局域网接口上使用 TLS，并打印配对链接 |
| `--network-port <port>` | 网络上的设备连接的端口；不指定就是 3443 |
| `--keep-awake` | 阻止主机休眠，免得手机用到一半被断开 |
| `--port`、`--no-open`、`--trusted-host` | 与上游行为一致；`--port` 仍然是本机自己用的端口 |

在 macOS 上，`--keep-awake` 使用 `caffeinate -i -w` 监视 dsh 进程；即使 dsh 被强制终止、未执行清理，闲置休眠抑制也会随进程退出而释放。Linux 上，`systemd-inhibit` 现在使用 GNU `tail --pid` 监视 dsh，进程异常退出后也会在短时间内释放抑制（需要 GNU `tail`；如果未安装，`--keep-awake` 会在启动时明确报出缺少该工具，而非继续启动）。Windows 上的 PowerShell 休眠抑制进程使用显式 UInt32 参数传入休眠标志（避免 Windows PowerShell 5.1 把高位十六进制字面量识别为负数），先获取 dsh 进程对象，初始化或运行时出错时立即失败（不会在报错后继续给出虚假的就绪信号），并要求 Windows 休眠抑制返回非空且非零的结果，确认成功后才等待 dsh 退出；如果系统拒绝抑制请求，辅助进程会报错退出，而非在未提供保护时继续等待。Windows 启动时会等到 PowerShell 在 Win32 休眠抑制成功后明确回报（最长 20 秒），如果失败或一直没有确认就拒绝启动；运行中意外退出仍会告警。如果启动确认失败，会尝试终止未确认的辅助程序；即使终止信号报错，也会最多等待七秒检查是否退出，再报告原始启动失败；如果无法确认清理完成，会警告可能有残留休眠抑制进程。 正常退出时，即使终止信号报错，也会继续有限时地检查辅助进程是否退出；若仍无法确认，会警告而不是让本插件的清理操作报错（上游子进程层还有独立的关闭规则）。设计上即使 dsh 被强制终止也会释放抑制，但仍待 Windows 实机验证。启动时只从 `PATH` 中的绝对目录查找休眠抑制工具（Linux 还包括 `tail`），忽略 `.` 等相对目录，避免选中工作目录中不可信的同名程序；找到后直接按绝对路径执行，不再重新搜索 `PATH`。如果没有符合要求的工具，`--keep-awake` 会明确拒绝启动。Windows 只选择原生 `powershell.exe`；DSH 的子进程不会通过命令解释器运行 `.cmd`/`.bat` 包装脚本，因此不会误把这些脚本认作可用的休眠抑制工具。此选项不阻止主动休眠，也不保证合上笔记本盖后仍能提供服务。

需要 dsh 0.1.5-rc.3 或更高版本，并针对 dsh 的最新版本测试。从 0.1.7 起，dsh 会自己检查这个最低版本：低于它的版本既不会安装这个插件包，也不会加载它，于是 `--host 0.0.0.0` 照旧被拒绝。更早的 dsh 不做这项检查；如果它还没有自带的浏览器登录（0.1.2 之前），这个插件会在启动时直接报错，并拒绝网络上的所有设备，而不是在没有登录的情况下对局域网敞开。

## 手机这边

拿手机对着终端里的二维码扫一下，配对就算完成了。链接里带着 dsh 的启动令牌，43 个随机字符，没人应该拿手机键盘去敲它。（链接也一并打印出来了，想发给自己也行。）

只有 TLS 监听器同时提供完整有效的 SHA-256 证书指纹和明确、有效的局域网 TLS 端口（`networkPort`），Lanyard 才会打印配对链接或二维码。同时会确认上游生成的令牌链接仍指向这个 HTTPS 监听地址的根路径，并且只有一个非空 `token` 查询参数，不带片段或其他参数。若指纹、端口缺失，链接的协议、主机、端口、路径不符，或上游生成链接时抛出异常，Lanyard 只记录不含令牌的固定错误信息，且**不打印任何配对链接或二维码**（包括其他网卡的备选链接）；不要自行拼接配对链接。如果更新 dsh 后遇到此情况，应检查插件兼容性，不要把可能包含令牌的上游错误原样复制到日志。如果启动时首次查询上游连接服务就抛错，或读取其 `authenticatedUrl` 属性时抛错，Lanyard 都会用固定的“缺少浏览器认证”错误拒绝配对，不传播可能包含令牌的上游异常。

如果已打印经过验证的 HTTPS 链接和证书指纹后，终端二维码生成失败，Lanyard 只记录固定且不含令牌的错误；此时仍可打开已打印的 HTTPS 链接，并照常核对证书指纹。这与 TLS 或上游配对链接不安全时完全不打印链接的情况不同。

第一次打开时，手机会提示证书不受信任：证书是在你电脑上自签的。先打开证书详情，把 SHA-256 指纹和启动行里打印的那个对一下，再点信任——要对全部，至少也要对前八组和后八组，因为只有几组相同的仿冒证书很容易造出来。对指纹是自签证书唯一的校验手段，所以手机每次问你都要对一遍——两边一旦对不上，就别继续了。在你确认之前什么都不会发出去，链接里的令牌也不会。

打开链接，手机就登录了：dsh 用令牌换出一个会话 Cookie，再重定向回不带令牌的地址，令牌随即从地址栏消失。之后直接输 `https://192.168.1.5:3443` 就能进，重启 dsh 也不受影响，直到会话过期为止——默认 30 天。想用起来更像个 App，可以添加到主屏幕。

如果已保存的 TLS 证书材料不完整（`cert.pem` 或 `key.pem` 只剩一个）、无法读取，或者证书与私钥不匹配，启动会停止并保留现存文件，即使局域网地址已经改变也是如此。请恢复完整且匹配的证书与私钥后再启动；Lanyard 不会悄悄丢弃手机之前信任的 TLS 身份。若 `cert.pem` 或 `key.pem` 是目标已丢失的符号链接，即使通常的文件存在性检查认为文件不存在，Lanyard 也不会擅自覆盖链接；请先修复链接或恢复匹配的证书与私钥。即使符号链接目前有效，自动管理的证书/私钥也会拒绝使用它：否则证书更新时的文件重命名会替换链接本身，悄悄断开原目标。请将已确认匹配的证书和私钥以普通文件形式恢复到仅所有者可访问的材料目录后重试。自动管理的目录、命名管道等非普通文件也会在读取前被拒绝，否则读取没有写入方的管道可能使 dsh 启动一直卡住。使用 `--tls-cert`/`--tls-key` 明确指定的 PEM 文件不受自动证书更新及所有权权限检查约束，但 TLS 前端会另行确认解析后的目标是普通文件；指向普通 PEM 文件的符号链接仍可使用。如果证书与私钥可读取且匹配，但证书已经过期或尚未生效，TLS 监听启动前会重新生成证书与私钥。更新后 SHA-256 指纹会改变；手机再次提示证书警告时，务必先核对新指纹再接受。 如果新私钥已写入但更新证书失败，Lanyard 会尝试恢复原来与旧证书匹配的私钥，之后可安全重试。如果文件发生意外变更或恢复失败，将拒绝覆盖并提示从备份恢复匹配的证书和私钥。进程或电脑在两次文件替换之间突然中断时，不保证原子恢复。

在 Linux/macOS 上，Lanyard 自动管理的 TLS 材料目录和已保存的 `key.pem` 必须仅允许文件所有者访问；从备份恢复后也一样。如果已有目录允许其他用户进入，或私钥允许组内/其他用户读取，启动会拒绝继续，不会擅自修改可能与其他程序共用的目录权限。确认归属后执行 `chmod 700 <材料目录>` 和 `chmod 600 <材料目录>/key.pem`，再重新启动。此检查仅针对 POSIX 下自动管理的材料；Windows 的 ACL、以及通过 `--tls-cert`/`--tls-key` 自行提供的证书私钥，需要操作者自行确保权限安全。

有三件事需要心里有数：

- **两台设备得在同一个网络里。** 链接用的是电脑的局域网地址，中间没有任何中转，数据也不出这个网络。电脑同时连着好几个网络时，二维码用的是最像家庭网络的那个地址，手机可能连得上的其他网络也会各打印一条链接（容器和虚拟机网络不算在内）。如果只找到这类网络，就不打印链接，并说明原因。
- **dsh 重启之前，这个链接就是密码。** 在那之前谁打开它，谁就登录了，所以别把它发到群聊里，也别把二维码留在别人看得到的屏幕上。重启 dsh 链接即作废，已经配对的手机不受影响。
- **换了网络就得换链接。** 会话绑定在打开它时所用的地址上。电脑的局域网地址变了，扫一下启动时新打印的那个即可。

## 配对之后，手机能碰到什么

**配对过的手机，就拥有你在这台电脑上的账号。** 它能用的东西里包括终端，以及一个会执行命令的 Agent，两者都以你的身份运行；所以你坐在键盘前能做的事，它都能做——包括直接手改 dsh 的配置文件。只配对你自己的设备；丢了一台，就当丢了一台登录着的笔记本电脑来处理。

留在本机的是界面里的配置类接口，而且网络上的设备碰不到任何没设防的路由：

- **只允许本机访问的部分**：设置、凭据、账号、模型服务商、安装或查看插件、任何会在这台机器屏幕上打开东西的操作，以及所有没有被明确归类过的 Gateway 命名空间和 `/api` 路由。这样凭据不会出现在手机屏幕上，手一滑也改不了这套安装的配置。但它挡不住你已经配对的设备——见上文。
- **格式错误的 HTTP 请求目标会在路由处理前被拒绝。** Node 的 HTTP 监听可能接收无效的绝对 URL，但后续 URL 解析会抛错；此时返回固定的 403，不让异常逃出处理器，也不让请求利用配对页和静态文件的公开豁免。
- **每一条路由前面都会校验 dsh 的会话**，不只是 dsh 自己把关的那些。某条路由的所有者忘了做校验，网络上的设备也照样进不去。如果上游会话校验函数、其属性读取或 Cordis 连接服务查询本身意外抛错，来自局域网的请求都会收到固定的拒绝响应，异常及可能包含的会话信息不会传出路由处理器。真正的本机回环请求仍免于此额外门禁；这些异常绝不等于局域网认证成功。
- **会话 Cookie 只在 TLS 里传输。** dsh 没有给它加 `Secure` 标记，这个插件在面向网络的监听上补上了；手机之后哪怕打开这台电脑上的某个 `http://` 明文地址，也不会把它明文发出去。
- **TLS 在进程内解密**，客户端的真实地址因此得以保留。如果换成端口转发，所有请求看上去都来自本机，会话校验和配置类接口的限制就都形同虚设。
- **界面自身的静态文件不受会话保护**。配对请求和这些文件走的是同一条路由，那时手机还没有会话；这些文件不含任何密钥，source map 也照旧被挡在外面。页面本身由 dsh 负责登录校验，页面跑起来之后发出的每个请求都需要会话。

## 已知限制

- **停止或重启 dsh 会断开手机连接。** 关闭服务时 Lanyard 会终止仍活动的 TLS 连接及未完成的握手，避免手机长期保持 WebSocket 导致主机进程无法结束。dsh 重新启动后再连接。此行为与 `--keep-awake` 的运行期间防止空闲休眠功能不同。
- **`--host 0.0.0.0` 指的是这台电脑连着的所有网络**——Wi-Fi、有线、VPN。这些网络上的任何设备都能连到 TLS 监听，只是没有会话就进不去。只在你信得过的网络里用，别在咖啡馆或酒店的 Wi-Fi 上开。
- **要让一台设备退出登录，只能让所有设备一起退出**。所有会话都由同一个密钥签发，也就是 dsh 凭据存储里 `client-connection` 的 browser-session 记录；替换它是唯一的吊销方式。
- **隧道等同于本机**。用 `adb reverse` 或 `ssh -R` 打通之后，手机在服务端看来就是本机连接：它仍然需要 dsh 的会话，但能碰到配置类接口。开这种隧道，相当于把键盘直接交给对方。
- **流式调用只能整体放行**。它们共用一条 WebSocket，这个插件只能整体放行或拒绝，看不到里面，所以配对过的手机有可能打开某个本应被拒绝的命名空间里的流——目前只有只读的账号状态，以及装了实验性语音插件包时它的流。同一条连接还承载着每个浏览器都会收到的通知，其中也包括配置方面的动静（某项设置或某个凭据改了、插件安装的日志），但不包含具体的值。界面的每次修改都是一次 HTTP 调用，每个调用都会单独归类，不过协议本身并不强制这一点。
- **和所继承的 Web 服务器、所依赖的登录机制绑定**。将来某个版本的 dsh 有可能让它失效；真出了问题会直接报错，不会悄悄退回明文，也不会放未登录的设备进来。

## 配置

正常情况下一项都不用改。默认配置是安全的，没列出来的一律拒绝。有几项值得知道：`pairedNamespaces` 和 `pairedRoutes` 决定配对过的手机能碰到哪些东西，没写进去的一律只允许本机，所以这个范围只会被有意放宽；`networkPort` 就是 `--network-port` 设置的那一项；`fallbackAdmission` 决定界面自身的静态文件怎么发，默认照发——改成 `gated` 的话，新设备就根本无法配对了。完整字段和覆盖方式见 [AGENTS.md](AGENTS.md)。
